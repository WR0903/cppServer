# 服务器进程架构与横向扩展文档

## 概述

本服务器采用**多进程分布式架构**，由 5 种核心进程协作组成完整的游戏服务器：

| 进程 | 类型标识 | 职责 |
|------|---------|------|
| **AppMgr** | `APP_APPMGR` | 中心协调器，管理所有进程信息、地图创建调度 |
| **Login** | `APP_LOGIN` | 登录验证、角色管理、Token 分发 |
| **Game** | `APP_GAME` | 游戏网关，管理玩家会话、地图代理（WorldProxy） |
| **Space** | `APP_SPACE` | 场景服务器，运行真实的游戏世界逻辑（移动、AOI、背包） |
| **DBMgr** | `APP_DB_MGR` | 数据库服务，MySQL 异步读写 |

此外还有一个特殊的 **AllInOne** 进程（`APP_ALLINONE`），将所有 5 种进程的组件合并到单进程中运行，适合开发调试。

### 连接关系总结

| 进程 | 监听端口 | 主动连接 |
|------|---------|---------|
| AppMgr | TCP + HTTP | 无 |
| Login | TCP | AppMgr, DBMgr, HTTP外部验证 |
| Game | TCP | AppMgr, DBMgr, Space |
| Space | TCP | AppMgr, DBMgr |
| DBMgr | TCP | 无 |

## 各进程详解

### 1. AppMgr — 中心协调器

**文件**: `src/apps/appmgr/`

#### 启动配置

```cpp
const APP_TYPE curAppType = APP_TYPE::APP_APPMGR;
// 监听 TCP（供其他进程连接）
// 监听 HTTP（供客户端查询 Login 地址）
```

#### 核心组件

| 组件 | 职责 |
|------|------|
| `AppSyncComponent` | 收集所有进程的状态信息，定时同步 Game 列表给 Login |
| `CreateWorldComponent` | 管理地图创建调度（公共地图 + 副本地图） |

#### 职责详解

**1) 进程注册与发现**

所有进程启动后主动连接 AppMgr，定时发送 `MI_AppInfoSync` 消息上报自身状态（AppId、AppType、在线人数）。AppMgr 维护全局进程表 `_apps`。

**2) HTTP 入口 — 客户端获取 Login 地址**

客户端首先通过 HTTP 请求 AppMgr，获取一个可用的 Login 进程 IP:Port：

```mermaid
sequenceDiagram
    participant C as Client
    participant A as AppMgr
    participant L as Login

    C->>A: HTTP 请求（获取Login地址）
    A->>A: 从 _apps 中选一个 APP_LOGIN
    A-->>C: 返回 {ip, port}
    C->>L: TCP 连接
```

**3) 地图创建调度**

```mermaid
flowchart TD
    A[Game 请求创建地图<br/>G2M_RequestWorld] --> B{地图类型?}
    B -->|公共地图| C{是否已创建/正在创建?}
    C -->|已创建| D[直接返回 worldSn]
    C -->|未创建| E[选一个 Space 进程]
    E --> F[发送 G2S_CreateWorld]
    B -->|副本地图| G{副本是否存在?<br/>G2M_QueryWorld}
    G -->|存在| H[返回 worldSn]
    G -->|不存在| I[返回失败]
```

**4) 容错处理**

当 Space 进程断线时：
- 正在创建的地图 → 重新选择其他 Space 进程创建
- 已创建的公共地图 → 从记录中删除
- 已创建的副本地图 → 从记录中删除

**5) Game 列表同步给 Login**

AppMgr 定时将所有 Game 进程信息（`MI_AppInfoListSync`）发送给所有 Login 进程，Login 据此为玩家分配 Game 服务器。

### 2. Login — 登录服务器

**文件**: `src/apps/login/`

#### 启动配置

```cpp
const APP_TYPE curAppType = APP_TYPE::APP_LOGIN;
// 监听 TCP（供客户端连接）
// 连接 AppMgr（上报状态、获取 Game 列表）
// 连接 DBMgr（查询/创建角色）
// HTTP 连接器（外部账号验证）
```

#### 核心组件

| 组件 | 职责 |
|------|------|
| `Account` | 处理登录全流程：验证、角色列表、创建角色、Token 分发 |
| `RedisLogin` | Redis 操作：在线标记、Token 存储、重复登录检测 |

#### 登录全流程

```mermaid
sequenceDiagram
    participant C as Client
    participant L as Login
    participant R as Redis
    participant H as HTTP验证服务
    participant D as DBMgr

    C->>L: 1. C2L_AccountCheck(account, password)
    L->>R: 2. SetnxExpire 检查是否已在线
    alt 已在线
        R-->>L: 在线
        L-->>C: 返回 ARC_ONLINE，断开连接
    else 离线
        R-->>L: 离线，继续
    end
    L->>H: 3. HTTP 验证 account + password
    alt 验证失败
        H-->>L: 失败
        L->>R: 清除 Redis 标记
        L-->>C: 返回错误码
    else 验证成功
        H-->>L: 成功
    end
    L->>D: 4. L2DB_QueryPlayerList(account)
    D-->>L: 角色列表
    L-->>C: L2C_PlayerList（角色列表）
    C->>L: 5. C2L_SelectPlayer(player_sn)
    L->>R: 6. 生成 Token，存入 Redis（带过期时间）
    L->>L: 7. 从 _apps 中选一个 Game 进程
    L-->>C: L2C_GameToken(ip, port, token)
    Note over C,L: 8. Client 断开 Login，连接 Game
```

#### Redis 使用

| Key | 用途 | 过期时间 |
|-----|------|---------|
| `account_online_login:{account}` | 防止重复登录（Login 阶段） | 短期 |
| `account_online_game:{account}` | 防止重复登录（Game 阶段） | 短期 |
| `account_token:{account}` | Login→Game 的验证 Token | 短期 |

### 3. Game — 游戏网关

**文件**: `src/apps/game/`

#### 启动配置

```cpp
const APP_TYPE curAppType = APP_TYPE::APP_GAME;
// 监听 TCP（供客户端连接）
// 连接 AppMgr（上报状态）
// 连接 DBMgr（查询/保存玩家数据）
// 连接 Space（转发游戏协议）
```

#### 核心组件

| 组件 | 职责 |
|------|------|
| `Lobby` | 大厅，处理 Token 验证、玩家数据加载、地图分配 |
| `WorldProxyGather` | 管理所有 WorldProxy 实例 |
| `WorldProxy` | 地图代理，1:1 对应 Space 中的 World，负责协议中转 |
| `WorldProxyLocator` | 全局地图定位器（worldId → worldSn） |
| `RedisGame` | Redis 操作：Token 验证、在线标记 |
| `SocketLocator` | Socket → WorldProxy 的映射 |
| `SpaceSyncHandler` | 处理 Space 同步消息 |
| `WorldComponentTeleport` | 跳转地图逻辑 |

#### Game 进入流程

```mermaid
sequenceDiagram
    participant C as Client
    participant G as Game(Lobby)
    participant R as Redis
    participant D as DBMgr
    participant A as AppMgr
    participant WP as WorldProxy
    participant S as Space(World)

    C->>G: 1. C2G_LoginByToken(account, token)
    G->>R: 2. 验证 Token
    alt Token 无效
        R-->>G: 失败
        G-->>C: 返回 TOKEN_WRONG
    else Token 有效
        R-->>G: 成功
    end
    G->>D: 3. G2DB_QueryPlayer(player_sn)
    D-->>G: 返回完整玩家数据
    Note over G: 4. 分析玩家上次所在地图
    alt 有副本记录且副本存在
        G->>G: Teleport 到副本
    else 进入公共地图
        G->>G: 检查 WorldProxy 是否存在
        alt WorldProxy 不存在
            G->>A: 5. 向 AppMgr 申请创建地图
            A-->>G: 返回 worldSn
        end
    end
    G->>WP: 6. Teleport: 玩家从 Lobby 移到 WorldProxy
    WP->>S: G2S_SyncPlayer（玩家数据）
    S-->>C: S2C_EnterWorld（进入确认）
```

#### WorldProxy — 地图代理

WorldProxy 是 Game 进程中最核心的组件，每个 WorldProxy 对应 Space 中的一个 World 实例：

```mermaid
graph LR
    C([Client]) <-->|TCP| WP["Game: WorldProxy"]
    WP <-->|TCP| W["Space: World"]

```

**职责**：
1. **协议中转**：客户端发来的协议 → 转发给 Space；Space 返回的协议 → 转发给客户端
2. **玩家管理**：维护当前地图中的玩家列表
3. **跳转处理**：处理 Teleport（跨地图跳转）
4. **默认处理函数**：未注册的协议自动中转（`HandleDefaultFunction`）

**WorldProxy 的 SN 编码**：WorldProxy 的 SN 由 Space 进程生成，因此可以从 SN 中提取出 Space 的 AppId（`_spaceAppId = Global::GetAppIdFromSN(_sn)`），用于精确路由消息。

### 4. Space — 场景服务器

**文件**: `src/apps/space/`

#### 启动配置

```cpp
const APP_TYPE curAppType = APP_TYPE::APP_SPACE;
// 监听 TCP（供 Game 连接）
// 连接 AppMgr（上报状态）
// 连接 DBMgr（保存玩家数据）
```

#### 核心组件

| 组件 | 职责 |
|------|------|
| `WorldGather` | 收集所有 World 的在线信息，定时同步给 Game 和 AppMgr |
| `WorldOperatorComponent` | 处理创建 World 的请求 |
| `World` | 真实的游戏世界实例，处理所有游戏逻辑 |
| `AoiComponent` | AOI 九宫格系统，管理玩家视野 |
| `MoveComponent` | 玩家移动组件 |
| `MoveSystem` | 移动系统（自定义 System） |
| `PlayerManagerComponent` | 管理 World 中的所有玩家 |

#### World — 游戏世界

每个 World 是一个独立的游戏场景实例，处理：

| 功能 | 说明 |
|------|------|
| 玩家进入 | `HandleSyncPlayer`：接收 Game 转发的玩家数据，创建 Player |
| 玩家离开 | `HandleG2SRemovePlayer`：跳转地图时移除玩家 |
| 移动 | `HandleMove`：更新位置、AOI、广播合并 |
| 外观同步 | `SyncAppearTimer`：定时广播新增/已有玩家外观 |
| 断线处理 | `HandleNetworkDisconnect`：存盘、从 AOI 移除、清理 |
| 背包 | `HandleBagSync` / `HandleItemUse`：背包同步和物品使用 |
| 定时存盘 | 每个玩家独立定时存盘 |

#### 地图创建流程

```mermaid
sequenceDiagram
    participant A as AppMgr
    participant S as Space
    participant G as Game

    A->>S: G2S_CreateWorld(worldId)
    Note over S: WorldOperatorComponent::HandleCreateWorld()
    S->>S: GenerateSN() → 生成 worldSn
    S->>S: CreateComponentWithSn<World>(worldSn, worldId)
    S->>A: MI_BroadcastCreateWorld
    S->>G: MI_BroadcastCreateWorld
    Note over G: WorldProxyLocator 收到广播
    G->>G: CreateComponentWithSn<WorldProxy><br/>(worldSn, worldId, lastWorldSn)
```

#### 移动广播合并

Space 中的移动不是每次都立即广播，而是采用**合并策略**：

```mermaid
flowchart TD
    A[玩家移动] --> B[缓存到 _pendingMoves<br/>同一玩家只保留最新位置]
    B --> C{每 200ms 触发<br/>FlushMovesBroadcast}
    C --> D[遍历所有缓存的移动]
    D --> E[通过 AOI 获取九宫格内的玩家]
    E --> F{人数超过 100?}
    F -->|是| G[按距离排序<br/>只广播最近的 100 人]
    F -->|否| H[广播给所有九宫格内玩家]
    G --> I[批量广播]
    H --> I
```

### 5. DBMgr — 数据库服务

**文件**: `src/apps/dbmgr/`

#### 启动配置

```cpp
const APP_TYPE curAppType = APP_TYPE::APP_DB_MGR;
// 初始化 MySQL 库
// 检查/更新数据库表结构
// 监听 TCP（供其他进程连接）
```

#### 核心组件

| 组件 | 职责 |
|------|------|
| `MysqlConnector` | MySQL 连接器，运行在 MysqlThread 上 |
| `MysqlTableUpdate` | 启动时检查/更新数据库表结构 |

#### MysqlConnector 特点

1. **运行在独立线程**：通过 `MysqlThread` 类型分配，不阻塞逻辑线程
2. **预处理语句**：使用 `MYSQL_STMT` 防止 SQL 注入，提高性能
3. **自动重连**：定时 Ping，断线自动重连
4. **Blob 存储**：玩家数据序列化为 Protobuf 二进制，存入 MySQL Blob 字段

#### 数据库操作

| 消息 | 操作 |
|------|------|
| `L2DB_QueryPlayerList` | 查询账号下的角色列表 |
| `L2DB_CreatePlayer` | 创建新角色 |
| `G2DB_QueryPlayer` | 查询完整玩家数据 |
| `G2DB_SavePlayer` | 保存玩家数据（定时 + 离线） |

#### 数据库表结构

```sql
-- player 表
CREATE TABLE player (
    sn BIGINT UNSIGNED PRIMARY KEY,  -- 玩家唯一 SN
    account VARCHAR(64),              -- 账号
    name VARCHAR(64),                 -- 角色名
    base BLOB,                        -- 基础信息（Protobuf）
    misc BLOB,                        -- 杂项数据（Protobuf）
    bag BLOB,                         -- 背包数据（Protobuf）
    savetime DATETIME,                -- 最后保存时间
    createtime DATETIME               -- 创建时间
);
```

```cpp
// allinone/main.cpp
const APP_TYPE curAppType = APP_TYPE::APP_ALLINONE;
// APP_ALLINONE = APP_DB_MGR | APP_GAME_MGR | APP_SPACE_MGR | APP_LOGIN | APP_GAME | APP_SPACE
```

## 横向扩展指南

### 扩展原则

本架构的横向扩展基于以下设计：
1. **AppMgr 是中心协调器**：所有进程向它注册，它负责负载均衡调度
2. **进程通过 AppId 区分**：同类型进程可以启动多个实例，各有不同的 AppId
3. **SN 编码 AppId**：全局唯一 SN 中包含 AppId 信息，可精确路由消息
4. **无状态设计**：Login/Game 不持久化状态，随时可增减实例

### 扩展 Login — 承载更多登录请求

**方法**：在 `engine.yaml` 的 `login.apps` 中增加实例：

```yaml
login:
  apps:
    - id: 101
      ip: 192.168.1.10
      port: 5401
    - id: 102              # 新增
      ip: 192.168.1.11
      port: 5401
    - id: 103              # 新增
      ip: 192.168.1.12
      port: 5401
```

**负载均衡机制**：
- 客户端通过 HTTP 请求 AppMgr 获取 Login 地址
- AppMgr 的 `GetOneApp(APP_LOGIN)` 从所有已注册的 Login 中选择一个（当前为随机/轮询）
- 每个 Login 定时上报在线人数，可据此实现加权分配

**无需额外处理**：Login 是无状态的（玩家验证完就断开），多实例之间通过 Redis 共享在线标记和 Token。

### 扩展 Game — 承载更多在线玩家

**方法**：在 `engine.yaml` 的 `game.apps` 中增加实例：

```yaml
game:
  apps:
    - id: 201
      ip: 192.168.1.20
      port: 5601
    - id: 202
      ip: 192.168.1.21
      port: 5601
    - id: 203              # 新增
      ip: 192.168.1.22
      port: 5601
```

**负载均衡机制**：
- Login 验证成功后，从 AppMgr 同步来的 Game 列表中选择一个（`GetOneApp(APP_GAME)`）
- 选择依据：在线人数最少的 Game 进程
- 玩家一旦进入某个 Game，后续所有操作都在该 Game 上

**注意事项**：
- 每个 Game 进程会为每个 World 创建一个 WorldProxy
- 同一个 World 在不同 Game 上有不同的 WorldProxy 实例
- 所有 WorldProxy 都连接到同一个 Space 上的 World

```mermaid
graph LR
    G1["Game-201<br/>WorldProxy-A"] --> S["Space-301<br/>World-A"]
    G2["Game-202<br/>WorldProxy-A"] --> S
    G3["Game-203<br/>WorldProxy-A"] --> S

```

- 不同的 World 可以分布在不同的 Space 进程上
- 每个 Space 进程可以承载多个 World 实例

```mermaid
    end

```

**容错**：Space 断线后，AppMgr 会将该 Space 上正在创建的地图重新分配到其他 Space。

---

### 扩展 DBMgr — 提升数据库吞吐

**方法 1**：增加 MySQL 线程数：

```yaml
dbmgr:
  thread_mysql: 5    # 从 3 增加到 5
```

每个 MysqlThread 运行一个独立的 `MysqlConnector`，可并行处理数据库请求。

**方法 2**：部署多个 DBMgr 实例（需要代码支持分库路由）。

当前架构中 DBMgr 是单实例的，如需多实例需要：
- 按玩家 SN 哈希分库
- 或按功能分库（角色库、日志库分离）

---

### 扩展总结

| 瓶颈 | 扩展方式 | 配置修改 | 代码修改 |
|------|---------|---------|---------|
| 登录并发 | 增加 Login 实例 | `login.apps` 添加条目 | 无需 |
| 在线玩家数 | 增加 Game 实例 | `game.apps` 添加条目 | 无需 |
| 地图承载 | 增加 Space 实例 | `space.apps` 添加条目 | 无需 |

| 数据库吞吐 | 增加 MySQL 线程 | `dbmgr.thread_mysql` | 无需 |
| 数据库瓶颈 | 分库分表 | 需要新增配置 | 需要 |

## 玩家完整生命周期

```mermaid
stateDiagram-v2
    [*] --> 获取Login地址: ① HTTP → AppMgr
    获取Login地址 --> 登录阶段: TCP 连接 Login

    state 登录阶段 {
        [*] --> 账号验证
        账号验证: Redis 防重 + HTTP 外部验证
        账号验证 --> 查询角色列表: DBMgr
        查询角色列表 --> 选择角色
        选择角色 --> 生成Token: Redis 存储
        生成Token --> 返回Game地址: L2C_GameToken
    }

    登录阶段 --> 进入Game: ③ TCP 连接 Game

    state 进入Game {
        [*] --> Token验证: Redis
        Token验证 --> 加载玩家数据: DBMgr
        加载玩家数据 --> 分析地图
        分析地图 --> Teleport: 从 Lobby 移到 WorldProxy
    }

    进入Game --> 游戏中: ④ WorldProxy ↔ World

    state 游戏中 {
        [*] --> 进入地图
        进入地图: SyncPlayer → EnterWorld
        进入地图 --> 游戏逻辑
        游戏逻辑: 移动、战斗、背包
        游戏逻辑 --> 定时存盘: Space → DBMgr
        定时存盘 --> 游戏逻辑
        游戏逻辑 --> 跳转地图: Teleport → 新 WorldProxy
        跳转地图 --> 进入地图
    }

    游戏中 --> 断线处理: ⑤ 网络断开

    state 断线处理 {
        [*] --> 通知Space: Game 检测断线
        通知Space --> 存盘清理: Space 存盘 + AOI移除
        存盘清理 --> 清除在线标记: Redis
    }

    断线处理 --> [*]
```
